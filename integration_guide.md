# Integration Guide: Backend A ↔ Backend B ↔ Backend C (ETL)

This guide shows how Backend A (NestJS), Backend B (Node/Express, this repo), and Backend C (ETL_service_pinntag) work together using a one‑way handshake and a shared MongoDB for B and C.

- Direction of calls: A → B, B → C (no inbound calls to A; C never calls B)
- Databases: A uses its own DB; B and C share the same MongoDB database
- Auth between services: API key via `X-API-Key` header

## Prerequisites

- Shared MongoDB URL configured for both B and C
- Backend C `.env` example:
  - `MONGODB_URL=mongodb+srv://.../pinntag_ai`
  - `API_KEYS=key_for_backend_b`  (comma-separated list supported)
  - `REDIS_URL=redis://localhost:6379/0`
  - Celery broker/backend configured (Redis by default)
- Backend B `.env` example for C integration:
  - `ETL_BASE_URL=http://<etl-host>/api/v1`  ← include version path
  - `ETL_API_KEY=key_for_backend_b`
  - `ETL_API_KEY_HEADER_NAME=X-API-Key`

## Orchestration Flow

1) Backend A requests ETL for a URL group from Backend B.
2) Backend B creates a Job document in the shared MongoDB (includes `jobId` and optional `groupId`), then calls Backend C to start the job by ID.
3) Backend C executes the ETL, updates job status/progress, and writes outputs to S3.
4) Backend B lists/reads jobs from the shared MongoDB and, once complete, imports processed outputs into its `scraped_events` collection for editing and verification.
5) Backend B exports approved events into Backend A’s database (A’s API).

## Job Document (created by Backend B)

Minimal shape expected by Backend C. Extra fields are allowed and ignored by C.

```
{
  "id": "3f2e8a8c-52f4-4db8-a7db-2ef8ea4f2c92",
  "status": "pending",
  "request": {
    "urls": [
      "https://example.com/event-1",
      "https://example.com/event-2"
    ],
    "source": "group-123",
    "output_formats": ["json", "parquet"]
  },
  "owner_id": "svc-b-or-user-123",
  "tenant_id": "tenant-abc",
  "tags": ["optional", "metadata"]
}
```

Collection: `jobs`

Required fields:
- `id`: string UUID generated by Backend B
- `request.urls`: non-empty array of URLs
- `request.source`: source/group identifier

Optional/ignored by C:
- `status` (C manages state transitions), `owner_id`, `tenant_id`, `tags`, other metadata

## Backend C APIs used by B

Base URL must include the version path (e.g. `/api/v1`). Backend B sets this in `ETL_BASE_URL`.

- Start job by ID (shared-DB lookup)

```
curl -X POST "http://<etl-host>/api/v1/jobs/<job_id>/start" \
  -H "X-API-Key: key_for_backend_b"
```

- Get job by ID

```
curl -s "http://<etl-host>/api/v1/jobs/<job_id>" \
  -H "X-API-Key: key_for_backend_b"
```

- List jobs (optional filters)

```
curl -s "http://<etl-host>/api/v1/jobs?status=completed&limit=50" \
  -H "X-API-Key: key_for_backend_b"
```

- Stream progress via SSE

```
curl -N "http://<etl-host>/api/v1/jobs/<job_id>/stream" \
  -H "X-API-Key: key_for_backend_b"
```

## Job States and Outputs

- States: `pending` → `running` → `completed` | `failed` | `cancelled`
- On completion, `outputs` contains S3 locations and counts, e.g.:

```
{
  "outputs": {
    "raw_data_path": "s3://pinntag-etl-raw/<source>/<job_id>/raw_data_YYYYMMDD_HHMMSS.json",
    "processed_data_path": "s3://pinntag-etl-processed/<source>/<job_id>/processed_data_YYYYMMDD_HHMMSS.json",
    "artifacts_path": "s3://pinntag-etl-artifacts/<job_id>/manifest_YYYYMMDD_HHMMSS.json",
    "record_count": 120,
    "unique_count": 110,
    "duplicate_count": 10
  }
}
```

Backend B typically reads `processed_data_path` to import into its `scraped_events` for editing.

## Backend B ↔ Backend C path alignment

Backend B’s ETL client calls the following relative paths under `ETL_BASE_URL`:

- `POST /jobs/:jobId/start` — instruct C to start a job by ID
- `GET /jobs/:jobId` — fetch job details
- `GET /jobs` — list jobs
- `GET /jobs/:jobId/stream` — stream updates (SSE/WebSocket)

Set `ETL_BASE_URL` to include the version segment from Backend C (e.g., `http://etl:8080/api/v1`).

## Error Cases

- 400: job already running or already finished
- 401/403: missing/invalid `X-API-Key`
- 404: job not found by ID

## Notes

- Backend C models tolerate unknown fields in job documents, easing interop with Backend B.
- If you prefer C to auto-start on DB insert (Mongo change streams) instead of the explicit start call, add a watcher in C as an enhancement.

# Backend A ↔ Backend B Integration

This section documents how Backend A (NestJS) integrates with Backend B (this service) to orchestrate ETL jobs and import verified events. Communication is one‑way: A calls B. Backend B does not call A.

## Auth

- Start ETL for a group:
  - Header: `x-internal-api-key: <PINNTAG_BACKEND_TO_AI_KEY>`
  - Enable by setting in Backend B `.env`:
    - `ENFORCE_INTERNAL_API_KEY=true`
    - `PINNTAG_BACKEND_TO_AI_KEY=<shared_secret>`
- Other B endpoints (events, jobs):
  - Optional auth via `AUTH_*` flags in Backend B. If enabled, A must include either an API key header or a bearer token per configuration.
  - Defaults are disabled (open) unless explicitly turned on.

## Workflow

1) Start ETL for a group on Backend B.
2) Poll job status and list jobs as needed.
3) Once complete, fetch verified events for that job from B and import into A’s DB.
4) Use the `markExported=true` option when fetching to avoid re‑importing the same events.

## Endpoints (Backend A → Backend B)

- Start job for a group
  - `POST /etl/groups/:groupId/run`
  - Headers: `x-internal-api-key: <PINNTAG_BACKEND_TO_AI_KEY>`
  - Body (optional):
    - `parameters`: object forwarded to ETL
    - `priority`: `low | normal | high` (default `normal`)
    - `metadata`: object persisted on the Job document
  - Response: `{ jobId, status }`

- Get job status
  - `GET /etl/jobs/:jobId/status`
  - Response: `JobStatus` object with `status`, `progress`, etc.

- List jobs
  - `GET /etl/jobs?groupId=<gid>&status=<s>&limit=50&offset=0`
  - Response: `{ items, total, hasMore }`

- Fetch verified events for import
  - `GET /etl/jobs/:jobId/verified-events?markExported=true`
  - Query:
    - `markExported=true|false` — when true, marks returned events as exported to prevent duplicates
  - Response: `{ jobId, exportedCount, events }`
  - Note: Use this endpoint to import into A. It returns only events that are verified and not yet exported.

- Optional: Fetch events with filters
  - `GET /etl/jobs/:jobId/events?verified=true|false&exported=true|false`
  - Response: `{ jobId, total, events }`

## Example requests

Start a group job

```
curl -X POST "http://b.local:4001/etl/groups/group-123/run" \
  -H "Content-Type: application/json" \
  -H "x-internal-api-key: <PINNTAG_BACKEND_TO_AI_KEY>" \
  -d '{
    "parameters": {"region": "us-east-1"},
    "priority": "normal",
    "metadata": {"requestedBy": "backend-a"}
  }'
```

Get job status

```
curl -s "http://b.local:4001/etl/jobs/<jobId>/status"
```

Fetch verified events and mark them exported

```
curl -s "http://b.local:4001/etl/jobs/<jobId>/verified-events?markExported=true"
```

## Data contracts

- Job status
  - Shape matches `JobStatus` in Backend B:
    - `id: string`, `groupId: string`, `status: 'pending'|'running'|'completed'|'failed'|'cancelled'`, `progress: number`, `error?: string`
- Scraped events
  - Rich schema with fields like `title`, `description`, `locations`, `schedules`, `categories`, etc.
  - Additional lifecycle flags used for import control:
    - `verified: boolean`, `verifiedBy?: string`, `verifiedAt?: Date`, `exported: boolean`, `exportedAt?: Date`

## Import strategy (recommended)

- Use job‑scoped imports: always fetch by `jobId` to batch events per run.
- Use `markExported=true` to avoid duplicate imports.
- Persist `jobId` and `event._id` in A as provenance for traceability.
- If retries are needed, the `exported` flag prevents re‑delivery of the same items.

## Security

- Allowlist Backend A’s outbound IPs to reach Backend B.
- Rotate `PINNTAG_BACKEND_TO_AI_KEY` periodically.
- If enabling `AUTH_*` on Backend B, provision A with the corresponding key/token and header (`AUTH_API_KEY_HEADER_NAME`, default `x-api-key`).

## Operational notes

- Pagination: `verified-events` currently returns all unexported verified events for a job. If large jobs require pagination, consider adding `page`/`limit` parameters to the endpoint in Backend B.
- Schema evolution: Backend B can add non‑breaking fields to events. Backend A should ignore unknown fields.
